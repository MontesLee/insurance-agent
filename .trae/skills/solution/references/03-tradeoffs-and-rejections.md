# 03 — 取舍与被否方向的设计依据

## 为什么必须显式写出取舍

"建议配置 X" 这类结论最大的问题是**不可审计**：不知道放弃了什么、为什么放弃。
策略层显式输出 `trade_offs[]`（含 `chosen` 与 `reason`）与 `rejected_directions[]`，
让下游与人工复核能看清决策路径，而不是只看到结论。

这也是 Lawgent 方法中"立场不可清洗"的体现：取舍是策略层的判断产物，
适配器与报告层只能原样传递，不得抹平或美化。

## trade_offs 结构

```yaml
- axis:     保障期限          # 在哪个维度上权衡
  option_a: 终身
  option_b: 定期（覆盖责任期）
  chosen:   定期（覆盖责任期）
  reason:   预算约束下优先覆盖家庭责任期，提高保障杠杆
```

`axis` 是维度，`chosen` 必须是 `option_a` / `option_b` 之一（由规则保证），
`reason` 给出可复核的依据。

## 各 domain 的默认取舍

| domain | axis | chosen | 核心理由 |
| --- | --- | --- | --- |
| `life` | 保障期限 | 定期（覆盖责任期） | 预算约束下优先覆盖责任期，提高保障杠杆 |
| `medical` | 保障范围 | 含目录外与免赔额以上 | 大额敞口在目录外与免赔额以上 |
| `critical_illness` | 赔付方式 | 确诊给付型 | 主要敞口是收入中断，不是医疗费用 |
| `accident` | 保障责任 | 含伤残分级与意外医疗 | 主要敞口是伤残收入损失，不是身故 |
| `savings` | 确定性 | 确定给付 | 长期现金流目标优先保证确定性 |
| `general` | 保障范围 | 综合责任 | 缺口性质未细化，先综合覆盖再拆分 |

这些是**领域默认**，不是客户个性化结论。个性化需要客户事实支撑，
而策略层不创造事实 —— 若未来要个性化，正确路径是增加规则分支 + 上游事实字段，
而不是让模型自由发挥。

## rejected_directions

| domain | 被否方向 | 理由 |
| --- | --- | --- |
| `life` | 终身寿险 | 保费占用预算较高且保障杠杆较低，优先以定期保障覆盖责任期 |
| `life` | 以储蓄型产品替代保障 | 保障额度与预算不匹配，无法覆盖责任期内的风险敞口 |
| `medical` | 仅依赖社保 | 社保目录外与起付线以上部分无法覆盖大额支出敞口 |
| `critical_illness` | 以医疗险替代重疾保障 | 医疗险按费用报销，无法覆盖收入中断与康复期支出 |
| `accident` | 仅配置意外身故责任 | 无法覆盖伤残导致的收入损失与意外医疗支出 |
| `savings` | 以高波动投资替代储蓄型保障 | 与长期确定性现金流目标不匹配 |
| `general` | 暂不处理 | 缺口已识别但性质未明确，需补充信息后再定策略 |

## "终身寿险"算不算产品名？

不算。`TERM_LIFE` / "定期寿险" / "终身寿险" 是**产品类别**（category），
与"某公司某款终身寿险"这种**具体产品**有本质区别。用户示例中
"采用定期寿险"正是类别层的表达。

判据：**能否直接购买？** 能直接买的是产品，还需要再选型的是类别。
策略层止步于类别。

## 品牌防泄漏

规则文件含 `forbidden_terms`（保险公司品牌名），单测扫描全部输出字符串。
但真正的结构性防线是**模板化**：所有文本来自规则，引擎没有自由文本入口，
因此品牌名在结构上无法产生。品牌列表是第二道防线（防止未来有人往规则里塞品牌名）。

注意品牌词选取需避免误伤：用多字完整品牌名（如"人保寿险"），
不用可能出现在正常语句中的短词（如"人保"会出现在"投保人保障"里）。
