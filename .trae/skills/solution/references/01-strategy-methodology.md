# 01 — 策略层方法论与边界

## 为什么需要独立的一层

把「缺口」直接翻译成「产品」会丢掉中间最关键的一步判断。同一类缺口（例如"家庭责任保障不足"）
可以对应完全不同的解决策略：定期寿险、终身寿险、提高现有保额、削减负债、增加被动收入……
选哪一种，取决于目标、约束与取舍 —— 这是**策略**，不是产品。

因此决策链必须有独立的一层：

| 层 | 回答什么 | 产物 |
| --- | --- | --- |
| Risk | 可能发生什么问题？ | `RiskAssessment` |
| Coverage Gap | 现在缺什么？ | `CoverageGapAnalysis` |
| **Solution** | **应采用什么解决策略？** | `SolutionPlan` |
| Product | 哪些产品可实现该策略？ | `ProductRecommendation` |

跳过后两层直接 Gap → Product，等于把策略判断偷偷塞进产品推荐里，既不可审计也不可复用。
未来若要增加「保单体检」「家庭保障盘点」「旧保单分析」，接口都落在 Gap 层；
若要增加「不同预算档位的方案对比」，接口落在 Solution 层。

## 策略层的能力边界

### 做

- 把每个 Gap 转成一条**方向性**策略（目标 + 保障方向 + 优先级）
- 显式表达**约束**（预算、已声明优先级、上游分析边界、增量补差）
- 显式表达**取舍**（在哪个维度上权衡、选了哪边、为什么）
- 显式表达**被否方向**（不采用什么、为什么不采用）

### 不做

- 不点名任何具体产品或保险公司 —— 那是产品层的事
- 不算具体保额 / 保费 —— 策略层没有、也不应臆造这些事实
- 不重算风险等级 —— 风险层已判定，策略层只引用 `risk_id`
- 不重判覆盖状态 —— 缺口层已判定，策略层只消费结论

## 反幻觉设计

策略层最容易产生的幻觉是「编造一个看起来合理的保额」。本 Skill 的防线是：

1. `coverage_direction` 只写**确定逻辑**（"以家庭责任与收入替代缺口确定保障额度"），
   不写数字。
2. 所有输出文本来自 `resources/config/solution-mapping.rules.json` 模板组合，
   引擎没有自由文本拼接入口。
3. 单测逐条比对 `coverage_direction == prefix[覆盖状态] + body[domain]`，
   任何偏离模板的输出都会 FAIL。
4. 无策略时用规则占位值，**不伪造** objective（契约要求 `minLength: 1`，
   占位值同时满足"非空"与"诚实"两个约束）。

## 为什么不用 LLM 自由生成

策略层若让模型自由写，必然出现：品牌名泄漏、编造保额、语气从"策略"滑向"推销"。
本 Skill 采用**确定性优先**：映射外置 + 模板组装 + 负向断言。
后续若要增强表达力，正确做法是扩充规则模板，而不是放开自由文本。
