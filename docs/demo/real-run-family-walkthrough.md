# 真实运行报告：一个三口之家的保险分析全过程

> **数据来源**：本机真实执行，非手写示例。
>
> - `python demo.py demo-c` → 案例 `bm-complete-001`（家庭全量需求）
> - `python demo.py demo-a` → 案例 `bm-complete-006-single-medical`（同一家庭，仅医疗需求）
>
> 下文所有数字、产品、判定均直接取自运行产出的 artifact 文件（`tmp/demo/<case>/artifacts/*.json`）。
>
> ⚠️ **所有产品来自演示目录（`is_demo = true`），是虚构的演示商品，不构成真实投保建议。**

## 二、每一步：输入 → 输出

### 步骤 1 · `client-intake` 客户信息结构化

- **输入**：客户的自述/录入信息（上游提供）
- **输出**：`client-profile` —— 结构化客户状态（即上表）
- **关键点**：每个字段都带 `status`（`KNOWN` / `UNKNOWN`）。缺失与冲突会被**显式标记**，系统不会"猜"。

### 步骤 2 · `requirement-analysis` 需求分析

- **输入**：`client-profile`
- **输出**：**5 条需求**

| 需求 ID    | 类型               | 内容       | 优先级             |
| -------- | ---------------- | -------- | --------------- |
| REQ-LIFE | life             | 家庭责任保障   | **P0_CRITICAL** |
| REQ-MED  | medical          | 大额医疗支出保障 | P1_HIGH         |
| REQ-CI   | critical_illness | 重疾收入补偿   | P1_HIGH         |
| REQ-ACC  | accident         | 意外医疗     | P2_MEDIUM       |
| REQ-SAV  | savings          | 长期储蓄     | P3_LOW          |

### 步骤 3 · `risk-analysis` 风险识别

- **输入**：`client-profile` + 需求
- **输出**：**5 条风险**

| 风险 ID  | 风险               | 优先级 | 严重度      | 已有保障         | 未保障金额    | 结论          |
| ------ | ---------------- | --- | -------- | ------------ | -------- | ----------- |
| R4-001 | 主要收入者身故导致家庭现金流中断 | P0  | CRITICAL | 已有定期寿险 200 万 | **0**    | 寿险已充分覆盖家庭责任 |
| R1-001 | 大额医疗费用支出         | P1  | HIGH     | 无            | **50 万** | 医疗风险无任何商业保障 |
| R2-001 | 重大疾病收入中断         | P1  | HIGH     | 部分重疾保障       | **70 万** | 重疾保额不足      |
| R3-001 | 意外伤残收入损失         | P2  | MEDIUM   | 已有意外险        | **5 万**  | 意外保障部分覆盖    |
| R5-001 | 退休现金流缺口          | P3  | LOW      | 无            | **30 万** | 无长期储蓄规划     |

### 步骤 4 · `coverage-gap-analysis` 保障缺口

- **输入**：风险 + 需求
- **输出**：**4 个缺口**

| 缺口 ID      | 领域 | 现状      | 级别       | 建议方向                    |
| ---------- | -- | ------- | -------- | ----------------------- |
| GAP-R1-001 | 医疗 | **无覆盖** | CRITICAL | 补充百万医疗险，覆盖社保外大额支出与免赔额缺口 |
| GAP-R2-001 | 重疾 | 部分覆盖    | HIGH     | 配置重疾险，保额覆盖 3–5 年家庭年收入   |
| GAP-R3-001 | 意外 | 部分覆盖    | MEDIUM   | 配置综合意外险（含意外医疗与伤残给付）     |
| GAP-R5-001 | 储蓄 | **无覆盖** | MEDIUM   | 建立长期储蓄 / 年金规划           |

> **值得注意**：寿险（R4-001）**没有产生缺口** —— 已保 200 万、缺口为 0。系统不会为了"多配置"而编造缺口。

### 步骤 5 · `solution` 解决策略

- **输入**：缺口
- **输出**：**4 条策略**（这就是"组合"的雏形）

| 策略 ID   | 类型               | 目标            | 优先级    | 对应缺口       |
| ------- | ---------------- | ------------- | ------ | ---------- |
| SOL-001 | MEDICAL          | 建立大额医疗支出保障    | **P0** | GAP-R1-001 |
| SOL-002 | CRITICAL_ILLNESS | 建立重疾收入补偿保障    | P1     | GAP-R2-001 |
| SOL-003 | ACCIDENT         | 建立意外伤残与意外医疗保障 | P2     | GAP-R3-001 |
| SOL-004 | SAVINGS          | 建立长期确定性现金流储备  | P2     | GAP-R5-001 |

### 步骤 6 · `knowledge-search` 证据检索

- **输入**：查询「百万医疗险 保障范围 免赔额 社保目录外 适用性 策略验证」
- **输出**：5 条证据，每条都带 `evidence_id` / `document_id` / `chunk_id`
  - `01_medical_insurance_001` ~ `01_medical_insurance_005`
- **关键点**：**只有医疗险的证据被检索到** —— 演示知识库里只有 `01_medical_insurance` 这一份文档。这一点直接决定了后面的结果。

### 步骤 7 ·  候选产品匹配

- **输入**：策略 + 产品目录（12 个演示产品）+ 证据
- **输出**：10 个候选 → **3 个准入（C001–C003）**，7 个被拒

**准入的 3 个（全部是医疗险）：**

| 候选   | 产品                           | 类型      | 可投保      | 证据                          | 对应                   |
| ---- | ---------------------------- | ------- | -------- | --------------------------- | -------------------- |
| C001 | **P001** demo-百万医疗险A（标准版）    | medical | ELIGIBLE | AVAILABLE（rollup=SUPPORTED） | SOL-001 / GAP-R1-001 |
| C002 | **P002** demo-百万医疗险B（长期保证续保） | medical | ELIGIBLE | AVAILABLE（rollup=SUPPORTED） | SOL-001 / GAP-R1-001 |
| C003 | **P003** demo-中端医疗险（0 免赔）    | medical | ELIGIBLE | AVAILABLE（rollup=SUPPORTED） | SOL-001 / GAP-R1-001 |

**被拒的 7 个（含原因码）：**

| 产品                     | 原因码                                                | 说明                        |

| 属性                    | 状态              |
| --------------------- | --------------- |

## 三、所以，这个家庭的保险组合是什么？

分两层回答：

### ① 规划层面 —— 系统给出的"组合"方向

| 优先级    | 方向        | 对应缺口                        | 建议动作                 |
| ------ | --------- | --------------------------- | -------------------- |
| **P0** | 大额医疗保障    | GAP-R1-001（**缺口 50 万，无覆盖**） | 补充百万医疗险              |
| P1     | 重疾收入补偿    | GAP-R2-001（缺口 70 万）         | 重疾险，保额覆盖 3–5 年年收入    |
| P2     | 意外伤残 / 医疗 | GAP-R3-001（缺口 5 万）          | 综合意外险                |
| P2     | 长期储蓄      | GAP-R5-001（缺口 30 万）         | 年金 / 长期储蓄            |
| —      | 寿险        | R4-001 缺口为 0                | **不建议加保**（已覆盖 200 万） |

### ② 产品层面 —— 系统实际敢点名的

只有**医疗**方向有证据支撑，因此只有 **P001 / P002 / P003** 通过了证据校验；重疾、意外、储蓄方向的产品**全部**因 `EVIDENCE_MISSING` 被拦截。

> **最终状态 = `INCOMPLETE_EVIDENCE`，primary = 0。**

## 四、为什么没有硬推一个"完整组合"？

这是**设计使然，不是缺陷**：

1. 演示知识库里只有一份文档 `01_medical_insurance`（医疗险）。重疾 / 意外 / 储蓄**没有任何可引用的条款证据**。
2. 规则规定：产品存在但没有对应知识证据 → `EVIDENCE_MISSING` → **不得作为有依据的推荐**。
3. 评估是 **Fail-Closed（失败即阻断）** 的：不可判定即失败，**不存在"先推荐了再说"的通道**。
4. 因此系统把结论停在 `INCOMPLETE_EVIDENCE` 并转人工复核，而不是用模型"记忆"编造一个看起来很完整的四险组合。

> **一句话**：它宁可说「我证据不够，不敢推荐」，也不说「我给你配齐了」。

## 五、对照实验：把需求收窄到"医疗"，推荐就落地了

同一个家庭，只保留医疗需求（案例 `bm-complete-006-single-medical`）：

- 需求：仅 REQ-MED ｜ 风险：仅 R1-001（未保障 50 万）｜ 候选：4 个
- **推荐状态：COMPLETE**

**最终推荐的组合：**

| 角色             | 候选          | 产品                        | 匹配度                                    |
| -------------- | ----------- | ------------------------- | -------------------------------------- |
| **主推 primary** | C001        | **P001 demo-百万医疗险A（标准版）** | strong_fit **1.0**，覆盖 REQ-MED / R1-001 |
| 备选 alternative | C002        | demo-百万医疗险B（长期保证续保）       | strong_fit 1.0                         |
| 备选 alternative | C003        | demo-中端医疗险（0 免赔）          | strong_fit 1.0                         |
| 不推荐            | C004 (P011) | demo-老年医疗保险C              | 不符合投保条件（35 岁）                          |

- **披露**：`is_demo = true`，`demo_products = [P001, P002, P003]`，`catalog_checked = true`，`unverified_products = []`
- **证据**：5 条（`01_medical_insurance_001` ~ `005`），全部可解析到 `chunk_id`
