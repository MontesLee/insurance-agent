# ADR-006 · Product Candidate / Recommendation separation

## Context
Early in V2, `recommendation` consumed `candidate_solutions` directly (generated by the solution
layer). The problem: **strategies contain no products** — no premium, no term, no eligibility, no
evidence. `recommendation` was effectively ranking a batch of "objects that cannot exist in any
product catalog", which is self-deception.

## Decision
Insert an independent layer:
`Product Catalog → product-candidate-provider → ProductCandidates → recommendation`.
- **The Candidate Provider only generates**: four deterministic checks (type / direction /
  eligibility / evidence) with labels (`admissible` plus reason codes); **no ranking, no primary
  pick**.
- **Recommendation only selects**: consumes real Catalog candidates and hard-rejects anything that
  fails product validation; three states `COMPLETE / INCOMPLETE_EVIDENCE / NO_CANDIDATES` are
  explicitly distinguished.

## Alternatives
- Keep strategy-level candidates: what gets recommended is a concept, not a product.
- Merge into one "generate and recommend" stage: self-certification within a single stage; cannot be
  independently validated.

## Why
Only by separating generation from selection can "are the candidates legal" and "is the selection
reasonable" be validated independently. This also makes `product_hallucination_rate` a testable
hard gate (target 0): every recommended product must exist in the Catalog.

## Trade-offs
- One more stage, one more dataset, one more contract (currently `product-candidates` is still a
  Skill-level schema; canonicalization is known tech debt).
- Eligibility depends on client facts (e.g. age); if upstream is missing, all candidates become
  `ELIGIBILITY_UNKNOWN` → correctly not recommended, but lowers the "has a recommendation" rate.
